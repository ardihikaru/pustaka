Measurement context

Taken with curl against pustaka serve on the same host (loopback), dev mode, warm page cache. Loopback removes network latency deliberately: the point is what the engine costs, not what your CDN costs. Add your real RTT to every latency figure.

Payload sizes

The interesting column is the last one. A full page load costs the HTML plus the shared assets; an in-site navigation costs only the article fragment, because the shell, CSS and JS are already in the browser.

So: ~16 kB gzipped for the first page of a session (HTML + CSS + JS + search index), then ~2.9 kB per navigation. There is no framework bundle and no hydration pass, because there is no framework.

Latency

Twenty sequential partial requests for a two-folder-deep page:

bash
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "%{time_total}\n" \
    localhost:8080/__pustaka/partial/guide/deploy/production.html
done | sort -n

# min 0.5 ms · median 0.8 ms · p95 20.6 ms

Read the p95 honestly

That 20.6 ms tail is not the request — it is dev mode re-reading changed files (a debounced rebuild fires roughly twice a second so you never restart while editing). Serve with --prod and the index is cached: the tail collapses toward the median. Dev mode trades a millisecond you can't feel for a workflow you can.

Index build cost

The search index is generated by parsing every registered page: extract <main class="doc">, strip scripts and tags, split on h2/h3, then build an inverted token index.

bash
$ time ./pustaka index ./docs > /dev/null
real  0m0.031s   # v0.5 baseline: 10 pages → 44 records incl. startup

Cost is linear in total page bytes, so a 500-page site lands in the low hundreds of milliseconds — still a startup detail, not a request cost. Search itself is an in-memory map lookup per token with set intersection across terms.

What the browser does

  • No build output. Pages are the source; there is no bundle to parse before first paint.
  • Charts are lazy. ECharts initialises through an IntersectionObserver, so a chart below the fold costs nothing until it scrolls into view.
  • Swaps replace one element. A navigation rewrites the contents of <main> and re-runs that page's scripts — the shell, listeners and search index survive untouched.
  • Static search stays small. Without the server, search runs over the ToC sections metadata already loaded with the registry — no extra request.

Reproduce it yourself

bash
P=$(curl -s -o /dev/null -w "%{size_download}" localhost:8080/guide/charts.html)
G=$(curl -s -H "Accept-Encoding: gzip" -o /dev/null \
      -w "%{size_download}" localhost:8080/guide/charts.html)
echo "plain=$P gzip=$G"
bash
# compare dev vs prod tails
./pustaka serve ./docs --addr :8080          # dev
./pustaka serve ./docs --addr :8081 --prod   # cached
bash
time ./pustaka index ./docs > /dev/null
./pustaka index ./docs | grep -c '"href"'   # record count

Where it would slow down

Being straight about the ceilings, since none of them are hit by this site:

  • Very large sites — the index is rebuilt whole, not incrementally. Past a few thousand pages, startup becomes noticeable and per-page caching would be worth adding.
  • Index over the wire — index.json grows with the site. Beyond a few hundred pages, prefer the server /search endpoint (already implemented) over shipping the whole index to the client.
  • Chart-heavy pages — ECharts is ~1 MB from CDN, cached across pages but real on a cold visit. Vendor and subset it if that matters for your audience.
  • Dev mode under load — the debounced rebuild is fine for authoring, wrong for production. Always ship --prod.
