Concept

Go + HTMX architecture

What replaces mkdocs’ Python build step: nothing builds. A single Go binary parses your HTML pages at startup, serves them, and lets HTMX swap only what changes.

Request flow

The first visit returns the full shell. Every navigation after that is an hx-get that replaces only the article region — sidebar state, scroll position of the drawer, and theme survive; the browser URL updates via hx-push-url.

Note — this prototype vs. production

Opened from disk, site.js injects the shell client-side and links do full page loads. Under pustaka serve the runtime auto-detects the server and upgrades itself: it fetches the generated index from /__pustaka/index.json and swaps only <main.doc> via /__pustaka/partial/… — the HTMX pattern, with the View Transitions API for animation. Page authors change nothing.

Search index at startup

The feature that must not regress from mkdocs. On boot, the server walks the docs folder, parses each page with Go’s x/net/html, extracts headings + text per section, and builds an in-memory inverted index. The prototype’s hand-written sections in toc.js disappear — they get generated.

go (sketch)
type Section struct {
    Page, Anchor, Title, Text string
}

func BuildIndex(root string) *Index {
    idx := NewIndex()
    walkHTML(root, func(page string, doc *html.Node) {
        for _, s := range splitByHeadings(doc) {  // h2/h3[id]
            idx.Add(s)                          // tokenize → posting lists
        }
    })
    return idx  // queries answer in-memory, no disk hit
}

Search queries hit GET /search?q=… and return a rendered result fragment that HTMX drops straight into the overlay — the same UI you see when pressing Ctrl K here, minus the client-side index.

Why not a SPA framework?

Docs are content, not app state. HTMX keeps pages as real HTML (perfect SEO, works with JS disabled) while still giving app-like navigation. And a Go binary deploys anywhere a file can.
