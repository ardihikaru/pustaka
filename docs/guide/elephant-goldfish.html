Guide

Design with an elephant, review with a goldfish

The model that wrote a page is the worst judge of it: it remembers what it meant to say. Pustaka splits the work in two — an author that knows everything, and a reviewer that knows only the page and the contract.

Two roles

The split comes from the Elephant-Goldfish Model (EGM), an open-source, Apache-2.0 workflow for designing and reviewing software with agents. The names describe memory: an elephant forgets nothing about the project, a goldfish remembers nothing but the page in front of it. Both are useful, and you need both, in that order.

RoleSeesDoes
ElephantEverything: the spec, the registry, earlier pages, the task, the conversation so far.Drafts pages and design documents.
GoldfishOnly the document under review and the sources it cites. No chat history, no project instructions file.Finds gaps the author can no longer see.
YouThe goals and the trade-offs.Accept or reject each finding, approve the pull request.

The rule

An author never approves its own draft. Review always happens in a new context that was given files, not a summary of the conversation.

How it maps onto Pustaka

Pustaka already had half of this: pustaka check is a goldfish. It remembers nothing and tests every page against the same rules every time. A second, model-based goldfish covers what a validator cannot test — whether a newcomer can follow the page, whether a number was invented, whether a page script survives partial navigation without a full reload.

1 · Elephant draftsai/SYSTEM_PROMPT.md
→
2 · Mechanical goldfishpustaka check ./docs
→
3 · Model goldfishpage + spec only
→
4 · Resolvefix or reject, check again

Steps 1–2 are the correction loop. Step 3 is new: start a fresh session, give it only the changed pages and ai/AUTHORING_SPEC.md, and ask for findings. Step 4 goes back to the author, which fixes each finding or says in one line why it rejects it.

The repository ships the loop as project skills and an agent under .claude/. They work on their own; installing the EGM plugin adds its reviewers and design skills.

Once the review of a design is resolved, egm-draft writes it to designs/<feature>.md; add it to designs/SITEMAP.md and commit both in the same pull request a human approves. Everything in .dev/docs/ stays local.

Other tools follow the same shape: run the author with ai/SYSTEM_PROMPT.md, then open a new chat for the reviewer and paste in only the page and the spec.

Where things live

Designs sit outside docs/ because everything under docs/ is the published site, and it stays HTML-only. Drafts and review reports are git-ignored: only the approved result is worth keeping, and a reviewer's raw notes would go stale on the next commit.

PathHolds
AGENTS.mdInstructions for any coding agent; CLAUDE.md imports it.
designs/Approved design documents and SITEMAP.md, their index. Outside docs/ on purpose: the published site stays HTML-only.
EGM.mdDirectory contracts — interface, invariants, side effects — at the root and next to the code they describe. Hand-written README.md files stay untouched.
.dev/docs/Drafts and review reports. Git-ignored; only the approved design is committed.

When to write a design first

Write a design in designs/ for a new engine command or route, a runtime behaviour change, a change to the authoring contract, or anything touching the login layer. Bug fixes and new documentation pages skip the design but still get a goldfish review. EGM's egm-drift-report compares the designs and contracts with the code; run it now and then so they stay true.

No AI required

Everything here is a convention. A design written by hand in the same template, reviewed by a colleague who was not in the room, is the same workflow.
